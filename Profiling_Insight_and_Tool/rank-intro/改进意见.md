## 一、这两级到底在回答什么

**一级（点一张卡 → `renderRankMem`）**：回答「**这张卡装了什么**」。

- 卡头两行：坐标（tp/dp/pp/ep · EP 组 · stage · L 段 · node/槽）+ 一句专家权重的 EDP 副本关系。
- 表体：自上而下 **碎片 → 激活 → 优化器态 → 梯度 → 权重**，顺序刻意和 3D 柱子从上往下一致（`segs.slice().reverse()`）。权重底下再缩进列出 8 个子块（attn.q/kv/out、router、experts、norm×2，加 stage0 的 embed、stage3 的 lm_head），每块标了「被哪把刀怎么切」。
- 末行：合计 / 64 GB + 余量。

**二级（再点某一行 → `memBlockDetail`）**：回答「**这一块自己是怎么来的**」，五件事固定顺序：

1. 口径（多少 GB = 多少 M 参数 × 每参数几字节；子块还给张量 shape）
2. 成分条 `compStrip`（只有权重档有）——宽度=字节占比，颜色=刀色
3. 体腔 `cavityBox3D`——三根轴各被自己那把刀切出格子，本卡持有那一格填实
4. 关系链 `memChainFig`——前向/反向/更新三行一环，说明这一档为什么整步放不掉
5. 对应通信（五元组：粒度/张量/前后 layout/源→宿/效果）+ 兄弟卡沿哪几根轴点亮

设计意图是清楚的：**一级答"多少"，二级答"为什么是这么多、跟谁凑一份"**。这个分工本身立得住。下面是问题。

## 二、业务表达上的问题

**1. 「规避溢出」是张空头支票（最严重）**

我把 128 张卡的账算了一遍：

```
合计区间  43.5 – 54.3 GB / 64 GB      占用率 68% – 85%
R0(stage0) 53.5   R32 46.8   R64 45.1   R96 48.3
```

**没有任何一张卡接近溢出**。`tr.t` 上那个 `.over` 红色类、`tot > cap` 分支在这份配置下是**死代码**。标题喊"规避溢出"，画面给的却是"人人余量 10–20 GB"——用户看完这一步学不到任何关于溢出的东西。

建议二选一：要么加一个可切的"危险配置"（比如 ga 拉到 8 让 stage0 的 in-flight 顶上去、或 ZeRO 关 + opt fp32×3 换成更贵的口径），让至少 stage0 那一排真的顶出壳外；要么老实把标题改成"往框里装内存，看份量从哪来"。现在这个标题是在给一个不存在的高潮做预告。

**2. 正文和画面直接打架**

第 8 步正文写着「**DP 是复制，不改变每张卡装多少**」。但 `memOf` 里 `actK` 是 `(0.74 + seed*0.62) * (0.95 + seed*0.10)`，同一个 stage 内不同 DP 组的激活实测：

```
stage0 激活 4.78 – 8.30 GB    (1.74×)
stage3 激活 1.25 – 2.03 GB
```

再加 `rsv` 的 1.1–2.7 GB 抖动。**同一行里 16 个 DP 组的柱子肉眼可见不一样高**，而正文刚说了"不改变"。用户只有两种解读：页面有 bug，或者正文骗人。

更麻烦的是：页面其实**知道**正确答案——`act` 的体腔图把 DP 当成了一根真轴（`{n:D.dp, dim:'dp', i:c.dp}`），意思是"DP 不改变尺寸、但激活的归属确实按 DP 分身"。这个精确的区分被埋在一张没有可见图注的线框图里。至少要在正文补一句：常驻三档 DP 确实不变，激活随路由不均波动、碎片按各卡分配历史不同。

**3. 交互深度和显存权重成反比**

```
优化器态  29.9–32.8 GB (61%)  → 二级只有一句话 + 一张链图，comm 为空
权重       5.0– 5.5 GB ( 9%)  → 二级有 8 个可展开子块 + 成分条 + 体腔 + 双通信
```

用户在 3D 里一眼看到的是那根最粗的紫柱（优化器态），点进去发现是全场信息最少的一档；而最细的权重柱反倒能钻两层。`opt` 那句 `note`——"面积最大的一档，也是'换 optimizer 能省多少'的全部战场"——是整个模块最有业务价值的一句话，结果它躺在 `title` 属性里（见下）。

这一档应该配一个可见的对比：`12B/参数 = 主参数 4 + m 4 + v 4`，并列上"换 bf16 optimizer / 开 ZeRO-1 各省多少 GB"。这才是"规避溢出"真正能落地的动作。

**4. 1F1B 的 stage 梯度埋得太深**

`stage0 激活 7.6 GB vs stage3 2.0 GB`，**3.7 倍**。这是 3D 场景里第一眼就能看出来的差异（四排柱子明显一排比一排矮），也是这屏最硬的一条业务事实。但解释它的 `cavityGrid`（"1F1B：stage 0 此刻压着 4 份"）要点两层才看得到。这条应该提到一级——比如激活那一行的 label 已经有 `in-flight 4μb` 了，但没说清"为什么 stage0 是 4、stage3 是 1"。

**5. 两行 `0.0 GB`**

`router` 6.3 MB、`norm×2` 0.2 MB，`fmtGB` 一律输出 `0.0`。表格里挂着两行"0.0 GB"的死行，而 `compStrip` 里它们因为 `w > 0.4` 过滤被直接丢掉——**图上没有、表上有**，两个视图不一致。建议这两行合并成一行"复制项（router + norm）< 0.01 GB"，或者把单位切成 MB。

## 三、视觉传达上的问题

**6. 所有图注都在 `title` 属性里（最严重的视觉问题）**

`fig(svg, cap)` 的实现是 `<div class="rm-fig" title="...">`。于是：

- `compStrip` 的「宽度=字节占比 · 颜色=切它那把刀」——**读懂这张图唯一的钥匙，不可见**
- `cavityBox3D` 的「①权重体 ℓ×h×e · 本卡 = 三根轴的交集那一格」——**不可见**，而这只盒子函数体里一个 `<text>` 都没有，是一只纯线框、零文字、只靠棱色暗示轴向的三维盒子
- 五档的 `note`（包括上面说的 optimizer 那句）——挂在一个 9px 的 ⓘ 上

原生 `title` 触屏完全不可用、延迟 1–2 秒、不可选中、深色模式下是系统白底。把整个模块最核心的解释托付给最弱的载体。至少 `compStrip` 和 `cavityBox3D` 的图注必须转成可见的 `.rm-note` 小字。

**7. `compStrip` 在这份配置下等于一根纯色条**

experts 占权重字节的 **90.5%**（stage0 含 embed 也有 82.4%）。标签阈值是 `w >= 28px`，210px 宽的条上：

```
experts  190px  ✓ 有标签
embed     18.8px ✗
attn.q     6.6px ✗
attn.out   6.6px ✗
attn.kv    3.3px ✗
router     0.25px → 连矩形都不画
norm×2     0.008px → 连矩形都不画
```

**永远只有一个可读标签。** 一条"成分条"退化成一块紫色 + 右端几条看不清的细缝，传达不了"成分"。这里要么改成对数宽度/断裂轴，要么干脆换成横向条形图（每块一行、按字节排序、条宽独立归一），后者在 210px 里反而说得清。

**8. 紫色一色三义**

同一屏里紫色同时是：

- 第 8 步的步骤主色 `#9F93D1`（`STEPS[7].color`）
- 优化器态 `MEM_BASE.opt = #9F93D1`（同一个值）
- EP 刀色 `VC.ep = #9B3CF6`

在 9px / 7px 的色块上，`#9F93D1` 和 `#9B3CF6` 很难分。于是"权重 → experts"那个子行的紫块，很容易被读成"和优化器态同色 = 有关系"。

**9. 一级表里两套色彩语法没有任何提示**

一级五档用 `MEMC`（档位色），权重展开的子行用 `cutColor` → `VC`（刀色）。视觉形式完全一样（色块 + 名字 + GB），色块大小 9px vs 7px 差别几乎看不出来，但**颜色的意思换了一套**。父行"权重"是蓝的，子行全是青/紫/灰，没一个跟父色有关系。需要在子块区上方加一条 6px 的说明或给子块区换个底纹来断开。

**10. `act` 的高亮色自相矛盾**

行高亮用 `--rmc: sg.c` = `MEMC.act`（**绿**），点开后二级标题 `tint = VC.dp`（**蓝**）。同一次点击，行是绿的、标题是蓝的。这个 `key === 'act' ? VC.dp` 的取色我理解是想呼应"激活的轴是 DP"，但它破坏了"点哪一行就是哪个颜色"的基本对应。

**11. 点之前 128 根彩柱无解**

3D 场景没有任何显存图例。五档的色-义对应表**只存在于 rankmem 卡内部**，而 rankmem 卡要点了卡才出现。正文说"点一张卡"，但用户在点之前看着 128 根五段彩柱，不知道哪段是什么。画布角上需要一个常驻的五档图例（第 8 步起显示）。

**12. 合计行没有水位感**

`合计 53.5 / 64 GB | 余量 10.5` 全是数字。整个步骤的主语是"水位"，却连一根 4px 的进度条都没有。建议在合计行下面加一条按 cap 归一的细条，五档同色分段 + 余量留白 + 64GB 刻度线——这一条能一眼回答"还剩多少"，比两个数字强得多，也是给第 1 点那个"溢出"做铺垫的地方。

**13. 分组标题不对称**

只在 `kind === 'model'` 时插了「模型态 · 哪一段归我」。列表开头的碎片、激活两行**没有标题**，读起来像漏了。exec 那两档该配一个对称的小标题（比如「执行态 · 这一步在压着什么」），顺便把"常驻三档 vs 流式两档"这个关键区分在一级就说出来——现在它只在 `act` 的 note 里（又是 `title`）。

**14. 340px 侧栏塞不下二级**

`.side` 是 340px 固定，扣掉 padding 和 rankmem 的 padding，内容宽约 248px。点开"权重"会在表格中间插入：成分条 + 体腔盒 + 关系链 + 两块通信五元组 + 兄弟卡行 ≈ 400px 高，把下面 8 个子块全推出滚动区。再点 experts 又插一段，且会**静默收起**父级的二级（`memSel` 是单值），用户在一个 `overflow:auto` 的容器里做两层手风琴，很容易丢失位置。

这是结构性的：二级那五件事（口径/成分/体腔/关系链/通信）信息量够撑一个独立面板。建议二级改成从右侧或底部推出的独立层，一级表保持稳定不被撑开。

**15. 术语提前泄漏**

卡头那句「专家权重与 EDP N 的 rank X 是同一份」对每张卡无条件显示，而且**点卡不受步骤限制**——第 1 步"一台机器"点 R3，就会弹出带 tp/dp/pp/ep/EP 组/stage/L 段的坐标行和 EDP 副本句。EDP 这个词在第 9 步才出场（`VC` 的注释自己写了"只在第 9 步的连线里用"）。坐标行应该按 `step` 裁剪，只显示已经引入过的维度。
