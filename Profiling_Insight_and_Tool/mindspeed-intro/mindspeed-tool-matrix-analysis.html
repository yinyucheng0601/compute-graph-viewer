01 / Repository reading

这个仓库到底做什么？

MindSpeed Core 是面向昇腾设备、适配 Megatron-LM 的大模型训练加速库。它不只是一个算子集合，而是围绕分布式训练执行栈，在并行、内存、通信和计算四个维度提供策略与实现。

P

并行编排

覆盖 TP / PP / DP / CP / EP、2D TP、自动流水与多种长序列并行，解决模型如何拆、放到哪里、何时执行。

mindspeed/core/*parallel*
M

显存治理

通过重计算、压缩、参数复用、Smart Swap、Attention Swap、自动 Pipeline 等方式，在容量和性能之间做取舍。

mindspeed/core/memory
C

通算优化

覆盖通算融合、通信掩盖、MoE All-to-All / AllGather 优化、AI QoS 等，降低多卡与大集群中的等待。

mindspeed/core + features
A

自动寻优

解析 Profile，建立算子、通信和内存模型，搜索候选并行配置，并推荐显存可行、性能靠前的方案。

mindspeed/auto_settings

02 / Current experience

它现在有界面或可视化报告吗？

简短答案：MindSpeed Core 自身没有原生 GUI，也没有直接生成 HTML / PDF 分析报告。它已经产出大量可视化所需的数据，但当前体验仍以命令行、结果文件和外部分析工具为主。

NATIVE UX · CURRENT

原生形态：CLI + 日志

训练和寻优通过 Python / Shell 参数启动。Auto Settings 会在终端打印搜索剪枝、OOM 淘汰和最终 Top-3 配置参数；搜索内部虽然使用性能与显存估计，但当前没有把它们组织成统一候选表、可交互漏斗或正式报告。

  • 看得到：推荐参数、剪枝 / OOM 信息、建模与搜索日志
  • 看不到：统一性能—显存表、淘汰原因分布、预测置信度、实验谱系
MACHINE OUTPUT

结构化结果

仓库会产生可供后续产品读取的 Profile 目录与中间数据。

  • 算子 / 内存明细：CSV
  • 通信与静态模型：JSON
  • 配置与运行信息：PKL
  • 推荐方案：终端日志对象
EXTERNAL VISUAL

外部可视化

仓库用户指南明确建议：采集性能数据后，使用 MindStudio Insight 查看算子耗时、通信占比、Timeline 等视图。

  • 已有：通用 Profile 图形化分析
  • 缺口：MindSpeed 策略搜索与优化建议的专属界面
→

UX 机会判断：不是从零创造数据，而是把已有日志、JSON / CSV / PKL 与外部 Profile 证据，统一成“搜索为什么这样选、问题应该怎么改、改后是否有效”的决策产品。

04 / Runtime dependency map

哪些不用拉任务，
哪些必须先让任务跑起来？

严格说应分成三档。“无需新拉任务”不等于“从零就有结果”：读取历史 Profile 可以离线进行，但历史数据本身仍来自先前的训练或采集任务；Auto Settings 也不是纯静态计算器，它会自动拉起短 Profiling。

GATE 0 · ZERO TRAINING RUN

无需拉起训练任务

输入只是源码、配置或已有外部数据，不依赖前向 / 反向执行。

查文档与配置规则

特性支持表、适用条件、参数模板、兼容与最佳实践可直接使用。

应用 / 撤销源码补丁

mindspeed -P / -R 修改 Megatron 源码，不启动训练。

数据预处理

tools/preprocess_data.py 可把用户自备数据转成 Megatron 格式；需要数据与 Tokenizer，但不需要训练 run。

准备启动配置

复制 Shell / YAML / Auto Settings profiling recipe，完成参数编辑与环境准备。

GATE 1 · REUSE EXISTING ARTIFACTS

无需新拉，但要有历史产物

当前可以离线消费文件；第一次获取这些文件时仍然需要运行任务。

查看既有 Profile

已采集目录可交给 MindStudio Insight 查看算子、通信、Timeline 与内存。

读取 Auto Settings 中间结果

现有 JSON / CSV / PKL、日志和工作目录可供二次分析或产品接入。

离线对比日志与指标

已有 Loss、吞吐、峰值显存、TFLOPS 与配置可以比较，不必重跑。

边界

仓库没有面向这些产物的统一 GUI 或稳定独立分析 CLI；直接接入需适配内部 schema。

GATE 2 · WORKLOAD REQUIRED

必须拉起训练 / Profiling 任务

能力作用于运行时执行链，或需要实际算子、通信和内存观测。

全部训练加速特性

TP / PP / CP / EP、重计算与 Swap、融合算子、通信掩盖、MoE、长序列、优化器等，都要进入 Megatron 前反向流程才会生效。

Profile / TFLOPS / DataDump / 精度看护

需要任务真实执行，才能产出耗时、shape、内存、通信、算子输出与 Loss 证据。

Auto Settings

会自动拉起多组裁剪后的短 Profiling，建立算子 / 通信 / 内存模型，再搜索 Top-3；可“以小仿大”，但不是零运行推荐。

Demo、系统测试与 Benchmark

脚本只是入口；验证精度、性能或显存仍需匹配的软件栈、数据和 Ascend NPU 任务。

DECISION RULE

只读“规则 / 脚本 / 配置”可零任务；读“已有结果”可不新拉任务；凡是要得到真实性能、显存、精度、通信证据，或让加速策略实际生效，就必须运行工作负载。这里的“任务”也包括 Auto Settings 自动发起的短 Profiling，并不一定是一次完整训练。

05 / Two typical usages

现在 MindSpeed 的两种典型用法

一种是“我已经知道要开什么优化，直接增强现有 Megatron 训练”；另一种是“组合太多不知道怎么配，让 Auto Settings 先建模再推荐”。

CASE 01 · DIRECT ACCELERATION

把现有 Megatron 训练迁到昇腾并定向优化

场景：32 层 Llama 长序列训练能运行，但单卡显存不足。团队不想降低序列长度，希望用 MindSpeed 的亲和适配和 Smart Swap 跨过 OOM。

BEFORE训练脚本已存在

Megatron 配置基本稳定，但在目标 NPU 配置上 OOM。

ACTION一行接入 + 特性参数

导入适配器，再按问题开启 Smart Swap、重计算或融合算子。

RESULT原脚本继续训练

MindSpeed 在训练执行链中完成 NPU 适配和内存策略。

# pretrain_gpt.py
import mindspeed.megatron_adaptor

# launch arguments
--optimization-level 2 \
--smart-swap
终端训练日志Loss / throughput可选 Profile 目录
CASE 02 · AUTO SETTINGS

用小规模 Profile 搜索大规模并行配置

场景：新模型准备扩到 64 卡，TP / PP / DP / CP / EP / MBS 组合过多。团队希望少跑实验，先得到显存可行且预测性能最佳的三组配置。

PROFILE自动拉起少量采样

裁剪网络并采集算子、通信和内存数据，支持“以小仿大”。

MODEL建模并剪枝

排除 OOM 方案，预测候选配置的耗时和峰值显存。

RECOMMEND输出 Top-3

终端打印推荐配置，工程师选择一组进行完整训练复核。

# 在原训练启动参数中追加
--auto-settings \
--auto-settings-type mixed \
--auto-settings-work-dir ./auto_settings_dir \
--auto-settings-ranks 64
搜索过程日志Top-3 configs性能 / 显存建模JSON / CSV / PKL

08 / Delivery roadmap

建议的三阶段落地顺序

先打通静态输入输出和解释层，再做真实 Profile 联动，最后才做持续运行中的实时闭环。这样能尽早验证用户价值，也避免一开始陷入平台工程。

PHASE 01 · 2–4 WEEKS

静态决策 MVP

  • 定义模型 / 集群 / 并行配置 schema
  • 接入 Auto Settings 结果 JSON
  • 完成搜索漏斗与 Top-3 解释卡
  • 输出启动参数与 Profile recipe
PHASE 02 · 4–8 WEEKS

Profile 证据联动

  • 接入算子、通信、内存解析结果
  • 图 / Rank / Timeline 跨视图联动
  • 建议绑定证据与适用条件
  • 基线与实验 run 因果对比
PHASE 03 · 8+ WEEKS

持续优化闭环

  • 训练中异常与策略状态回放
  • MoE 专家迁移、Swap 可视化
  • 回归守门与批量实验管理
  • 团队级知识沉淀与报告审计
先定义数据契约

前端不要直读散落 CSV。用稳定 schema 表达 config、candidate、evidence、action、result。

区分预测与实测

所有数字必须标注来源、版本、置信度；预测值与 Profile 实测值不可混成同一口径。

建议必须可回滚

每个优化动作都保留原配置、变更 diff、风险和验证门槛，避免“黑盒一键优化”。
