Without the agent

能力很多，入口却分散。

用户往往先花时间识别仓库、版本、后端和工具边界，真正的工程工作反而排在后面。

  • 同一句“优化”可能指训练、推理或算子
  • 仓库别名、历史名称和技术栈容易混淆
  • 操作散落在文档、脚本和个人经验里
  • 给出建议不等于完成验证与交付
INTENT ROUTING

With MindSpeed Agent

一句话进入正确工作流。

Agent 先用生态知识图谱做确定性消歧，再按任务形态决定调用单点 Skill，还是进入多角色状态机流水线。

  • 歧义时明确反问，不静默猜仓库
  • 只按需安装命中的领域插件
  • 复杂任务由设计、开发、测试、检视协作
  • 用命令、配置、代码与报告形成证据链

01 / How it works

一句话，怎样走到结果？

路由不是“猜一个最像的 Skill”。它先确定目标仓与任务维度，再结合插件安装状态和执行形态，决定下一步由谁做、做到什么程度。

01 · INTENT接收自然语言模型、目标、现象、环境信息都可以不完整。
02 · REPO生态仓消歧按 id 与别名表识别训练框架、推理引擎或工具栈。
03 · TASK识别任务类型迁移、性能、精度、部署、诊断、算子、资料或验证。
04 · UNIT选择插件单元检查是否已安装；未安装时给出对应平台命令。
05 · EXECUTEAgent / Skill 执行单点任务直达 Skill，复杂任务进入多角色流水线。
06 · VERIFY证据与验收保留真实命令、配置差异、测试结果和边界结论。
CONSTRUCTED WALKTHROUGH
“vLLM-Ascend 上的 Qwen3 服务 P99 太高，帮我完成诊断和优化，并证明没有精度回退。”

这不是一个“给几条建议”的问题，而是一条需要设计、实测和回归的端到端任务。

ROUTING TRACE
  1. REPOvllm-ascend（推理目标仓）
  2. TASK KINDdiagnose + perf-optimize + validate
  3. PLUGINinference-model-optimize
  4. ENTRYorchestrator 状态机入口
  5. AGENTSarchitect → developer → tester → reviewer → optimizer
  6. DELIVERY基线、Profile 证据、配置改动、性能对比、精度验收

03 / Product architecture

不是技能清单，
是三层协作架构。

Plugin 负责流程与边界，Agent 负责角色协作和决策，Skill 提供领域知识与工程模板。复杂任务可以稳定编排，单点任务也能直接命中最小能力。

LAYER 01 · ORCHESTRATION

Plugin

定义一个领域的入口、安装单元、Agent 协作顺序和状态机工作流。

  • core + 按需 unit
  • 安装与平台边界
  • 状态、门禁与交付契约
LAYER 02 · EXECUTION

Agent

承担设计、开发、测试、检视、优化等角色，把需求分解为可检查的阶段。

  • 上下文与方案决策
  • 角色间交接
  • 失败定位与迭代
LAYER 03 · KNOWLEDGE

Skill

最小知识单元，封装领域步骤、工程约束、工具用法和可复用模板。

  • 按场景精确加载
  • 仓库内单一知识源
  • 可评审、可演进、可组合
不静默猜测

仓库或任务不唯一时明确列出差异，请用户确认关键分岔。

按需加载

core 保持轻量，只有命中领域才安装对应插件并新开会话。

真实证据优先

命令输出、配置 diff、测试与报告优先于无依据的“应该可以”。

边界可见

明确区分已有能力、需要环境才能验证的能力与规划中的能力。

04 / Start small

先装 core，
然后直接说需求。

三个平台共享同一套 catalog、Skills 与工作流。路由命中尚未安装的领域时，Agent 会给出按需安装命令；新 unit 安装后需要新开会话加载。

最好的入口不是命令，
是你的真实问题。

例如：
“我想优化 MindSpeed-LLM 的模型，但不知道先看性能、精度还是并行配置。”

core 会先完成消歧。如果任务仍有多个合理方向，它会展示选项，而不是替你悄悄做决定。
