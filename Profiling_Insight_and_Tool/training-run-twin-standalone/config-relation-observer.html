          章节目录

            把一份训练配置调对，本质上是在一张互相牵制的约束网里找可行点： 五个并行维度不是五个独立的旋钮，它们彼此相乘、又同时被模型结构、集群拓扑和单卡显存三面夹住。 这份文档写的就是这张网 —— 每条约束从哪来、违反了会怎样、以及某一项调不动时该动哪一项。 约束卡左缘的色条是类别：红=硬约束（违反则起不来），橙=软约束（能起来，但踩在性能悬崖上），蓝=取决于所用框架的口径。

            一份配置要过三关

            三关的失败方式完全不同，代价也差着数量级：

            关要满足什么不满足时
            配得通并行维度的乘积对得上卡数，整除关系自洽启动器当场拒绝，秒级失败
            切得开切分维度整除得了被它切的模型结构框架建图时报错，分钟级失败
            跑得下最紧的那张卡装得下前几个 step OOM —— 而这时通常已经排了几小时队

            越靠后的关卡，失败成本越高：前两关是确定性的整数运算，开训前就能算死； 第三关要把权重、梯度、优化器状态、激活和运行时开销逐项估出来， 但它同样是算得出来的 —— 不必等 OOM 才知道。

            Total Layer decoder 层数 · num_layers Model Architecture

            堆叠多少个 transformer decoder block。它是模型结构参数，不是并行参数 —— 改并行度只是换个方式跑同一个模型，改层数则是换了一个模型，权重不再通用。

            DP Data Parallel · 数据并行度 Model Architecture

            同一份完整模型被复制多少份，每份吃不同的数据分片，每步末把梯度 all-reduce 到一致。 副本之间是复制关系而不是切分关系。

            它解决的是「算得太慢」，不是「装不下」 —— 这是五个维度里唯一一个加了不省显存的。把 DP 从 2 拉到 8，总卡数翻两番， 每张卡上的权重、梯度一个字节都没少。唯一的例外是权重分片 —— 拨到 ZeRO-1 时优化器状态沿 DP 维分片，拨到 FSDP2 时权重与梯度也跟着切。 本页 Model Architecture 那一行就有这枚三档控件， 拨一下容量柱当场变矮（见 term-parallel-optimizer）。

            PP Pipeline Parallel · 流水线并行度 Model Architecture

            把模型按层切成若干段（stage），每段放一组卡上，micro-batch 像流水线一样依次流过： 第一段算完把激活传给第二段，自己接着算下一个 micro-batch。

            它解决的是「单卡放不下这么多层」。在五个维度里它的通信量最小 —— 相邻 stage 之间只传一份边界激活，而且是点对点，不是集合通信。 正因如此，PP 是最适合切在节点边界上的一维。 代价是流水线气泡：首尾填充与排空阶段有卡在空转，比例约 (PP − 1) / micro_batch_num。

            调大
            • 单卡装不下这么多层，且不想加通信更密的 TP
            • 要跨节点扩展 —— PP 通信最稀，最扛得住跨机
            调小
            • 气泡占比过高（micro-batch 数喂不满流水线）
            • 层数不够分，出现空 stage
            • stage0 在飞的激活反成瓶颈（PP 越大它压得越多）
            PP
            一定联调
            • Total Rank —— 乘积变了
            • Total Layer —— 必须 ≥ PP
            • VPP —— 层数要被 PP × VPP 整除
            • 各 stage 的层数划分与首末段的额外负担
            考虑再调
            • Micro Batch —— 压气泡要更多 micro-batch
            • VPP —— 压气泡的另一条路，代价落在激活上
            • Node —— PP 最适合切在节点边界
            VPP Virtual Pipeline · 虚拟流水（交错式 1F1B） Model Architecture · 高级选项

            把每个 PP stage 上的层再拆成 VPP 段，让同一张卡轮流跑属于自己的第 1 段、第 2 段…… 卡数一张不变（VPP 不进 world 的乘积），变的只是这些层在时间上怎么排。

            它收在 Model Architecture 行的「高级选项」折叠里，判据就是上面这句： 那一行留在明面上的五枚恰好是 world 乘积的因子加模型自身的层数， 拨了 Total Rank 一张卡都不变的一律收进折叠。 真实调参的顺序也对得上 —— 先 DP/TP/PP/EP 把模型装下，再用重计算与权重分片挤余量， VPP 是量到气泡占比之后才动的第二梯队旋钮。

            它治的是流水线气泡：非交错 1F1B 的气泡比例约 (PP − 1) / m， 交错之后每一段变短、流水线填得更快，气泡按 1/VPP 缩小。 但气泡不是白省的 —— 代价整个落在激活峰值上： warmup 段要多灌几份 micro-batch，每张卡同时压着的未反向激活变多。

            本页按 Korthikanti et al. 2022 §2.2 的口径算这笔账， 逐 stage 给出在飞份数 [2(PP−s−1) + (VPP−1)·PP + 1] / VPP； s = 0 时它正好化简成那篇论文给的整体惩罚因子 PP · (1 + (PP−1)/(PP·VPP))。 直观结果是：「各 PP Stage 峰值」那排小柱整体抬高、而且变平 —— 末段抬得比首段还多（PP=4 / VPP=2 时首段在飞 4 → 5.5 份，末段 1 → 2.5 份）。

            它比 PP 严格：层数必须被 PP × VPP 整除。 本页的 PP 允许不均分（46 层分 4 段 = 12,12,11,11），交错式流水不允许 —— 每一段都得等长。 这一条在默认预设上会立刻咬人：openPangu 的 46 层连 PP=4 都除不尽， 所以 46 % (4 × VPP) 对任何 VPP > 1 都不为 0，默认档下 VPP 只能是 1。 按一下加号，页面会把 Total Layer 抬到 48（唯一一个改了不连累卡数的对手字段）， 这时 VPP 才有 2 / 3 / 4 / 6 / 12 可选。

            ⚠️ 本页只建模 VPP 的调度代价，不改层→stage 的画法。 真实的交错式流水下 stage0 持有的是分散在全模型各处的几段（chunk 0、chunk 4……）， 而 Layer 导航、整网 deck、集群矩阵仍按连续分段显示。 改这一处要动 deck pattern 的 stageRanges 契约（它收的是连续区间）， 范围远超这一条，故明确记为已知简化。

            调大
            • 气泡占比高，而 micro-batch 数已经加不动了
            • PP 大、单卡显存却还有余量
            调小
            • 激活已是瓶颈 —— VPP 只会让它更紧

            • stage 间通信次数按 VPP 倍增，跨机时不划算
            VPP
            一定联调

            • 单卡显存的激活段（在飞份数变多）
            • 不动 Total Rank —— VPP 不占卡
            考虑再调

            • 重计算 —— 激活被抬高之后常常要往上拨一档
            TP Tensor Parallel · 张量并行度 Model Architecture

            把单个算子的权重矩阵按行或列切开，多张卡各算一片，再把结果拼回去。 切的是注意力头和 FFN 的 intermediate 维。

            它是见效最直接的一维 —— 参数和激活一起降，而 PP 只降参数、CP 只降激活。 代价也最重：每层前向反向各要 all-reduce 一次激活，是通信最密的维度， 而且这些通信都在关键路径上、无法与计算重叠掉。 所以 TP 组一旦跨出节点就是性能悬崖 —— 吞吐可能掉一半以上。

            本页把这条整除关系落成了硬校验：TP 必须同时整除 num_heads 与两个 intermediate，也就是它们公约数的因子。 openPangu 是 gcd(48, 9216, 1024) = 16 → 可取 1/2/4/8/16； Qwen2 是 gcd(28, 18944) = 4 → 1/2/4。 头数是模型常量、不是可调字段，撞上它时没有「改另一个数来兼容」的修法 —— 所以加减键会跳过除不尽的档位，到顶之后加号直接置灰，而不是让你步进到一个报错态里去。 n_kv_heads 则不硬拦：GQA 下 TP 超过 KV 头数只是把 KV 复制一份， 功能上合法、通信与显存变差，页面按软警告提示 —— 与「TP 组跨节点」同一档。

            调大
            • 显存缺口大且要立刻见效（两头一起降）
            • 单层权重本身超过单卡容量
            调小
            • TP 组被迫跨节点
            • 头数 / KV 头数 / intermediate 除不尽
            • 切得太碎，矩阵乘掉出高效区间
            TP
            一定联调
            • Total Rank —— 乘积变了
            • 单卡显存（参数与激活同时变）
            • 受 num_heads / intermediate 整除约束（n_kv_heads 除不尽只警告，不拦）
            考虑再调
            • Node —— TP 组必须收在节点内
            • 序列并行开关（决定激活还能不能再切一刀）
            CP Context Parallel · 上下文并行度 Model Architecture

            把一条序列按 token 位置切成若干段分给不同卡。 attention 要看全局，所以各卡之间还要把缺的那部分补回来 —— 怎么补有两种做法，见下面的 CP 口径。

            它专治长序列。激活随序列长度线性增长，attention 的中间量甚至是平方级 —— CP 是唯一直接压这一项的维度。序列不长时它没有意义：白付一轮通信， 而省下的激活本来就不是瓶颈。

            它的硬约束跟着口径走，不是一条固定的式子。 页面早先只按 ring attention 一种口径建模，把 seq % (2×CP) == 0 当成 CP 的通用约束 —— 但那是 ring 专属的（因果注意力下序列前段计算量远小于后段，得对半交叉分配才能均衡负载）。 Ulysses 沿头维切，序列长度多少都行，约束改落在 num_heads % (TP × CP) == 0 上。 两条都已落成硬校验，都只在 CP > 1 时生效 —— CP=1 时两档说的都是同一件「不切」，此时 CP 口径 那枚控件也是灰的。

            调大
            • 序列拉长后激活爆了
            • attention 的中间量已是显存主要来源
            调小
            • 序列本来就不长，CP 只是白付通信
            • Ring 档：序列长度除不尽 2×CP
            • Ulysses 档：TP × CP 除不尽头数

            CP 口径 Ulysses / Ring —— 上下文并行的两种算法 Model Architecture · 高级选项

            CP 切成几份由 CP 那枚 stepper 定；这一枚定的是切完之后 attention 怎么把「要看全局」补回来。 两档都让每张卡只留 S/CP 份激活，所以单卡显存完全相同 —— 拨这一枚，容量栏一个数都不会变。差别在通信形态与硬约束上。

            UlyssesRing
            怎么补进 attention 前一次 all-to-all，换成「每卡整条序列、一部分头」，算完换回来各卡只持自己那段的 KV，沿环轮转传给邻居，边传边算

            并行度上限头数（48 头的模型，TP × CP 最多 48）没有上限，序列想切多细就切多细
            attention 内核不用改，FlashAttention 原样能用要改写成分块累加
            通信形态一次性 all-to-all，在关键路径上逐块点对点轮转，可与计算重叠

            怎么选：头数够切就用 Ulysses —— 实现最省事，MindSpeed MM 的特性表里多数模型标的就是它， 本页也以它为默认档。头数不够切（TP × CP 已顶到 num_heads）、 或序列长到十万 token 以上，就换 Ring。两者还能混用（hybrid：外层 Ring、内层 Ulysses），本页未建模。

            这一枚是页面上唯一一个会换掉硬校验本身的控件 —— 同一组 TP / CP / Seq Length，在一档下合法、在另一档下报红字。 页面此前只有 Ring 那一条，等于对走 Ulysses 的配置画了一条错误的红线； 这一条正是为治那个而加的。

            序列并行 SP use_seq_parallel · Sequence Parallel Model Architecture

            TP 只切得动矩阵乘那一段，LayerNorm / Dropout 前后的残差流在 TP 组内是整份复制的。 SP 把这部分也沿序列维切给同一个 TP 组 —— 不额外占卡、不新增通信量 （原来的 all-reduce 拆成 reduce-scatter + all-gather，总字节数不变）。

            它没有自己的并行度 —— 切成几份由 TP 决定，所以表单里它只有开与关， 不像 DP / TP / CP 那样有 1/2/4 的档位。 所以它几乎是白拿的：只要 TP > 1 就该开。 TP=1 时没有 TP 组，也就没有「在组内复制」这回事 —— 本页此时把这枚开关置灰并强制关掉（悬浮会说明原因）： 留着一个开着却改不动的它，只会在 YAML 里留下一行没人能解释的 use_seq_parallel: True。 注意它和 CP 切的是同一个维度但目的不同：CP 为了长序列而多占卡，SP 只在已有的 TP 组里做文章。

            关

            词表走 DP vocab_emb_dp · Embedding 的两种放法 Model Architecture

            词表矩阵是全模型最大的单块权重：vocab × hidden， 151552 × 2560 ≈ 388M 参数 —— 光权重加梯度就 1.5 GB， 权重分片拨在「关」时连同优化器状态共 6.2 GB。 它有两种放法 —— 走 DP（在 TP 组内整份复制，每张卡背满） 或走 TP（沿词表维切成 TP 份，每卡只背 vocab/TP 行）。

            默认是走 DP，而且不是随手选的：切开之后每次查表都要一次通信把散在各卡的结果拼回来， 而词表矩阵虽大、算得却很轻，这笔通信常常不划算。 代价是它不随 TP 变小 —— TP=1 时两档数字一模一样（÷1，此时本页把开关置灰）， 一提 TP 就分道扬镳：其余权重都在缩，只有它原地不动。 Embedding 又只压在 Stage0、LM Head 只压在末 Stage， 所以「各 PP Stage 峰值」那排小柱首尾两根会越来越突兀 —— 那就是它。

            关（走 TP）

            重计算 recompute_config · 激活重计算，四档 + 「重算层数」 Cluster

            前向不留每层的中间激活，反向要用时按需重算一遍前向。 它是拿算力换显存，而且汇率极高：每层激活从 34·mb·S·H 掉到 2·mb·S·H（只留层输入），差一个数量级，代价约 +30% 的算力开销。

            与并行维度的根本差别是：并行维度靠多加卡把东西分摊出去，重计算不加一张卡 —— 所以显存不够时它常常是第一个该试的旋钮，而不是最后一个。

            五个并行维度各切什么

            五个维度切的是完全不同的东西，这决定了它们各自的通信代价， 也决定了加它到底能不能换来显存余量：

            维度切什么通信省显存？
            DP切数据，每副本一份完整权重每步末 all-reduce 梯度一次不省
            PP切层，每卡只背本 stage 那几层相邻 stage 点对点传激活，最稀省
            TP切张量：注意力头、FFN 的 intermediate每层前反向各 all-reduce 一次激活，最密省
            CP切序列长度看口径：Ulysses 一次 all-to-all 换头 / Ring 逐块轮转 KV省激活
            EP切专家，每卡只持有一部分路由专家MoE 层 all-to-all 收发 tokenMoE 下省得最多

            VPP 不在这张表里，因为它不是第六个维度。 它一张卡都不多占（不进 world 的乘积），也不切任何东西 —— 只是把本卡已有的那几层再拆成 VPP 段轮流跑，换的是更小的流水线气泡。 它反过来吃显存：在飞的 micro-batch 变多，激活段抬高。详见 term-vpp。

            「显存不够就加卡」只有加 TP / PP / EP / CP 时才成立。 把 DP 从 2 拉到 8，总卡数翻两番，每张卡上的权重、梯度、优化器状态一个字节都没少 —— DP 副本之间是复制关系而不是切分关系。DP 买的是吞吐，不是余量。

            这条有一个重要的例外：把权重分片拨离「关」之后，权重相关的字节会沿 DP 维分片。 由于优化器状态通常占权重相关字节的四分之三 （fp32 master weight + momentum + variance 共 12 字节，对 bf16 的 2 字节权重）， 这一档对显存的影响往往比再加一维并行还大。

            但 ZeRO-1 和 FSDP2 切的不是同一批段，别混成一句话说： ZeRO-1（enable_parallel_optimizer）只切优化器状态，权重与梯度仍是整份； FSDP2 是 ZeRO-3 口径，三段全切，代价是每层前反向都要把那一层的权重 all-gather 回来。 近两年不少新模型的首发配方直接就是「纯 DP + FSDP2 + 重计算」， 对这类配置按 ZeRO-1 估会高出一大截。 本页已如此落地：Model Architecture 行的「权重分片」三档控件直接改容量柱 —— ZeRO-1 只动优化器段，FSDP2 连权重段与梯度段一起压下去、并在预留段里加一笔 all-gather 暂存； 分母三档共用，专家按 EDP 分、其余权重按 EDP × EP 分 （两者都是同一批卡数，与 EP 口径无关）。

            world_size 与 rank 编址

            并行维度的乘积就是这次训练要占的卡数，它必须等于启动器实际拉起的进程数 （msrun 的 --worker_num、torchrun 的 nproc × nnodes）。 对不上时启动器不会替你猜，直接失败。

            world_size = DP × PP × TP × CP × EP ← EP 独占 rank 的口径 world_size = DP × PP × TP × CP ← EP 从 DP 切出的口径（见下一节）

            全局 rank 号怎么排

            把五个维度的坐标压成一个整数，通常按这个顺序展开 —— stage 最外，EP / TP / CP 最内：

            r = s·(DP·EP·TP·CP) + d·(EP·TP·CP) + p·(TP·CP) + c·TP + t n = ⌊r / 每节点卡数⌋ s 层所在 PP stage d DP 序号 p EP rank t TP 序号 c CP 序号 n 物理节点号

            这个顺序不是随意的。越靠内的维度，同组的 rank 号越连续， 也就越可能落在同一个物理节点内、走机内互联而不是跨机网络。 所以通信最密的维度（TP）排在最内层，通信最稀的维度（PP）排在最外层 —— 编址顺序本身就是一次通信优化，而不只是编号习惯。

            层与专家怎么落到维度上

            • 层 → PP stage：尽量均分，前 L mod PP 段各多 1 层。 46 层切 4 段 → 12, 12, 11, 11。首段还要多背 embedding，末段多背 LM head， 所以各 stage 天然不等重。
            • 专家 → EP rank：等分连续切，p = ⌊e / (E / EP)⌋。 每个 EP rank 拿到 E / EP 个专家。

            切出式的意思是：一张卡既是某个数据并行副本的成员，又是某个 EP rank 的持有者。 这是 Megatron 系（含 MindSpeed-LLM）的做法 —— EP 不进 world_size 的乘积， 而是把已有的 DP 组再切一刀。切完之后专家权重只在剩下的 DP / EP 维上复制， 这一维就叫 EDP（expert data parallel）。

            第三档：MindFormers 在 DP×MP 域上切

            MindSpore / MindFormers 的 expert_parallel 同样不占额外的卡， 但它切的域不是 DP，而是 DP × MP（mp 就是 model_parallel，即 TP）—— 一个 EP 组的成员既跨数据并行、也跨张量并行。约束因此换成 (DP × TP) % EP == 0，而 EDP = DP×TP/EP。

            不补这一档，一份真配置就读不进来。MindFormers 的 DeepSeek-V3 参考配置写的是 dp:4 / mp:8 / pp:8 / ep:32：按「从 DP 切出」算 4 % 32 除不尽、当场报错； 按「正交」算 4×8×8×32 = 8192，而它实际只有 256 张卡。 只有在 dp×mp 域上 4×8 = 32 才整除得开。

            这一档还有一个连带后果：TP 不再是独立的一根轴。 集群矩阵里横着的那 EP 张卡本身就横跨了 TP， 所以一张卡的 TP 分片号要从它在域里的位置反推 （(EDP索引 × EP + EP索引) % TP）， 而路由专家只 ÷EP、不再另 ÷TP —— EP 已经吃掉了 mp 那一维。

            ⚠️ 本页按专家张量并行 ETP = 1 建模。真实 MindFormers 里专家自身还能再切 TP， 那时严格的约束是 (DP × TP) % (EP × ETP) == 0，专家权重还要再 ÷ETP —— 那一档本页没有建模，遇到写了 expert_model_parallel 的配置要自己折算。

            同一组数字的两种读法

            以 openPangu 2.0 flash 的参考配置为例： DP=8, PP=4, TP=1, CP=1, EP=64，总共 2048 张卡。

            正交读法： 8 × 4 × 1 × 1 × 64 = 2048 DP 就是 8 切出读法： DP = 2048 / (4 × 1 × 1) = 512 EDP = 512 / 64 = 8 ← 配置里写的那个 "8"

            两种读法算出来的总卡数一样，但「DP」指的不是同一个东西： 正交读法里它是数据并行度，切出读法里那个 8 是专家的数据并行度，真正的 DP 是 512。 看一份配置时，判断依据是它跑在什么框架上，而不是字面。

            那一个 batch 到底切几份

            切 512 份。切数据的只有 DP 这一维 —— 全局 batch = MBS × DP × 梯度累积步数， 这里的 DP 是 512 而不是 8。EDP 那个 8 复制的是专家权重，不是数据。

            同一个 PP stage 上的 512 张卡 = 8 行 × 64 列 （PP=4 → 这样的网格共 4 张，合起来才是 2048） ├─── EP = 64 列，合持一整套 256 个专家（每卡 4 个）───┤ ep0 ep1 ··· ep63 EDP0 dp0 dp1 ··· dp63 EDP1 dp64 dp65 ··· dp127 ··· ← 共 8 行 = 专家权重的 8 份副本 EDP7 dp448 dp449 ··· dp511 每格 = 一个 DP 副本在这一 stage 上的那张卡，各吃一份数据分片 横向 all-to-all 收发 token · 纵向 all-reduce 专家梯度

            注意 EP 组是横着跨副本的。一个 DP 副本自己只有 PP×TP×CP = 4 张卡， 而那 4 张卡是 4 个不同的 stage —— 它们装不下、也不需要装下一整套 256 个专家。 同一层的专家永远散在同一个 stage 的那 64 张卡上，而这 64 张卡分属 64 个不同的 DP 副本。 某个 token 被 router 打给第 200 号专家，all-to-all 就把它横着送到 ep50 那张卡 （也就是 dp50 在这一 stage 上的卡）去算，combine 再送回来。 所以一份 1/512 的数据照样能路由到全部 256 个专家 —— 靠的是借用另外 63 个副本的卡，而不是在自己那 4 张卡里打转。

            但这趟横向搬运不是又一次数据切分。dispatch 前和 combine 后， 每张卡手里都还是它原来那一份 1/512 的数据 —— token 只是出去算了一趟就回来了。 切数据的始终只有 DP 这一维。

            由此带出一个容易被忽略的后果：同一次训练里，两拨参数的梯度聚合域不一样大。 attention、dense、共享专家这些每张卡都持有一份的参数，梯度要在 512 张卡上 all-reduce； 而路由专家的参数横向被 EP 切开了，同一个专家全局只有 8 份副本， 它的梯度只在那 8 张卡之间 all-reduce。EDP 的真实身份就是这个 —— 专家参数的梯度聚合域，不是数据切分的份数。

            反例：DP 不被 EP 整除会怎样

            切出口径下 DP % EP == 0 是硬约束，而它为什么硬，看一个具体的数就清楚了。 设 EP=64、每个 MoE 层 256 个路由专家 —— 一张卡持有 256 / 64 = 4 个专家，凑齐一整套专家要 64 张卡。 此时若 DP=120：

            EDP = 120 / 64 = 1.875 ← 不是整数 前 64 张：epRank 0–63 → 专家 0–255 ✓ 完整一套 余 56 张：epRank 0–55 → 专家 0–223 ✗ 缺 224–255

            问题不在那 1.875 本身，而在余下的 56 张卡组成了半套专家。 这半套照样在跑数据并行 —— 拿到自己的数据分片、算完 attention、进 router —— 但 router 一旦把某个 token 打给第 240 号专家，all-to-all 在这半套里找不到持有者。 这不是精度差一点的问题，是通信域里根本没有那个对端： 实际表现通常是建图或通信域初始化阶段直接报错，跑不到第一个 step。

            而同一组数字换到正交口径就完全合法：DP=120 与 EP=64 是两根独立的轴，world = 120×PP×TP×CP×64，每个 EP rank 都有自己独占的卡， 每个 DP 副本自带一整套 256 个专家（它横跨全部 64 个 EP rank），120 份都完整， 凑不齐半套的情形根本不会出现 —— 这正是正交档不需要 DP % EP == 0 的原因。 同一份数字合不合法取决于口径 —— 这是这一章最实际的用处。

            这个反例在页面上可以亲手拨出来，两条路径的表现刻意不同：

            • 直接在 DP 框里键入 120 —— 页面会把 DP 与 EP 一起标红、 停止更新所有图形（矩阵与容量柱停在上一组自洽参数上）， 并在表单下方给出建议修法与「一键应用 / 取消修改」两个出口。 手输是「精确指定」，页面不会替你改别的数。
            • 点 DP 的加减键往下拨到 32（加减键只走 2 的幂档位）—— 你不会看到错误，而是会看到 EP 自己跟着收到 32： 加减键是「联动配平」，页面把它当作必须的联动改动当场修掉了。
            值得注意的是：正交与切出两档下卡的排布是同一个。 那 512 张卡本来就该排成 8 × 64 的网格 —— 区别只在于你把行叫做「DP」还是「EDP」。 也正因为如此，这个混淆很难被卡数对不上暴露出来，只能靠事先问清楚。 点集群矩阵里任意一格看到的关系也完全一样：一张卡只连一个 EP 组 （外加共享专家 —— 它每张卡上都有一份，不参与 EP 切分）， 两种口径下连的是同一个组、同一批专家编号。 这两档的开关改的只有两件事：world 公式里乘不乘 EP，以及矩阵纵轴该叫 DP 还是 EDP。
            但第三档不一样 —— 它真的会改排布。 MindFormers 档的 EP 是从 DP × MP 域里切的， 横着的那 EP 张卡因此横跨了 TP： 行数从 DP/EP 变成 DP×TP/EP， 一张卡的 TP 分片号也不再是「格子在行内的第几个」， 而要从它在域里的位置反推。 换句话说，前两档是同一张网格的两种读法， 第三档是另一张网格。

            切分维度与模型结构的整除关系

            每个切分维度都在切某个具体的模型结构量，切不整就无处安放。 这一组是最常见的「配置看着合理、一建图就报错」的来源。

            num_layers ≥ PP 硬约束

            每个 pipeline stage 至少要分到 1 层，否则会有空 stage 占着卡什么也不算，还要在流水线里占一拍。

            层数除不尽 PP 是允许的（多出来的层分给靠前的 stage），少于 PP 才是错。

            num_heads % TP == 0 硬约束

            TP 切的是注意力头，每张卡分到整数个头。 头数常常不是 2 的幂（如 48、28），而 TP 习惯上按 2 的幂取，两者很容易对不上。

            建图阶段报维度不匹配，报错信息通常指向 QKV 投影的权重形状。

            n_kv_heads % TP == 0　（GQA / MQA 模型） 硬约束

            GQA 的 KV 头数远少于 Q 头数（如 28 Q : 4 KV），它才是真正卡住 TP 上限的那个数。 TP 超过 KV 头数就得把 KV 复制到多张卡上 —— 显存与带宽都白付，多数框架直接拒绝。

            这是 GQA 模型 TP 开不大的根本原因，和参数量无关。

            intermediate_size % TP == 0 硬约束

            FFN 沿 intermediate 维切。MoE 模型的 moe_intermediate_size 往往比 dense 的小一个数量级 （典型值 1024 对 9216），所以同一个模型里 MoE 层比 dense 层更早卡住 TP。

            即使整除得开，切得过碎也会让矩阵乘掉出高效区间，性能先垮在切分粒度上。

            本页两条都已落地：除不尽是红色报错（TP 的可选档位因此收成 gcd(头数, intermediate) 的因子），每卡分片薄于 256 是黄色性能提示。

            seq_length % (2 × CP) == 0　（Ring 口径） 硬约束

            CP 沿序列维切分。要求 2 倍而不只是 CP，是因为因果注意力下序列前段的计算量远小于后段， ring attention 要把序列对半交叉分配才能让各 rank 负载均衡。

            这是 ring 专属的一条，不是 CP 的通用约束。 页面早先按它一条建模，等于对走 Ulysses 的配置画了一条错误的红线； 现在它只在 CP 口径 = Ring 时生效。

            num_heads % (TP × CP) == 0　（Ulysses 口径） 硬约束

            Ulysses 沿头维做 all-to-all，而 TP 早已先切过一轮头 —— 两者争的是同一批注意力头，所以要整除的是它们的乘积。 这同时就是 Ulysses 的并行度天花板：48 头的模型，TP × CP 最多到 48。

            本页已落成硬校验，并且两枚 stepper 会互相让路：TP 到顶时加号置灰并说明「CP 也在切同一批头」， 反过来也一样。这是页面上第一条把两个可调字段绑在一个乘积上的约束。

            num_layers % (PP × VPP) == 0 硬约束

            交错式 1F1B 把每个 stage 的层再拆成 VPP 段轮流跑，每一段都得等长。 这比 PP 自己严格：PP 允许不均分（46 层分 4 段 = 12,12,11,11），VPP 不允许。

            本页已落成硬校验。它在默认预设上立刻咬人 —— openPangu 的 46 层连 PP=4 都除不尽， 所以默认档下 VPP 只能是 1；按一下加号，页面会把 Total Layer 抬到 48 （唯一一个改了不连累卡数的对手字段）。

            num_experts % EP == 0 硬约束

            路由专家要能均分到每个 EP rank。除不尽意味着有的卡多背一个专家， 这一维的显存与计算量当场就不齐了 —— 而 all-to-all 是同步的，最慢的那张卡决定整层的耗时。

            top_k ≤ num_experts 硬约束

            一个 token 选不出比总数还多的专家。

            Top-K 还决定 all-to-all 要搬多少 token，以及 MoE 算子临时区的峰值 —— 见「单卡显存由什么构成」。

            DP % EP == 0 依实现而定

            只在「EP 从 DP 切出」的口径下成立。要求的对象是 EP 组而不是 DP 副本： 切出档下一个 DP 副本本来就不持有整套专家，凑齐一套要横着的 EP 张卡 —— 集群矩阵的一整行，也就是一个 EP 组（token 的 all-to-all 就在这个域里收发）。 除不尽意味着末尾剩下的卡凑不满一个完整的 EP 组， router 打过去的 token 在域里找不到对端。 EDP = DP/EP 是这样的完整组共有几个（专家权重的副本份数），不是那一行的名字 —— 纵向同一列的 EDP 张卡持有的是同一份 E/EP 个专家。 DP=120 / EP=64 的具体反例见「EP 与 DP」一章。 EP 正交的口径下没有这条 —— 那里每个 DP 副本横跨全部 EP rank，自带一整套专家。 严格写法还要把专家内部的张量并行算进去：DP × TP % (EP × ETP) == 0。

            并行维度落到物理拓扑上

            前一组约束来自模型，这一组来自机器。它们的共同点是：都不在模型定义文件里， 却同样能让一份配置跑不起来 —— 或者跑起来慢得没意义。

            总卡数 % 节点数 == 0 硬约束

            每节点卡数要是整数，且这个数由硬件形态定死（昇腾 910B 一节点 8 卡），不是可以随便填的量。

            本页已按这条把 Node 做成只读派生量（Total Rank ÷ 每节点卡数），所以它不再可能被违反。

            TP 组不跨节点：TP ≤ 每节点卡数 软约束

            TP 每层前反向都要 all-reduce 一次激活，是通信最密的一维，必须吃机内互联。 一旦 TP 组跨出节点，这些 all-reduce 全部落到跨机网络上 —— 带宽差着数量级， 而它们又都在关键路径上，无法与计算重叠掉。

            这是典型的性能悬崖：配置合法、训练能跑，但吞吐可能掉一半以上。本页在表单下方用一枚黄色横幅「性能提示」说出来（形状与红色报错横幅相同，只是换了颜色），不拦截、不冻结图形 —— 它是让你知情，不是替你否决。

            EP 的 all-to-all 域尽量收在超节点内 软约束

            EP 越大，MoE 层 dispatch/combine 的 all-to-all 参与方越多。 all-to-all 的代价随参与节点数增长，而且它天然是全连接通信模式，对拓扑最敏感。 大 EP 省下的显存，可能被跨机 all-to-all 的时间吃回去。

            表现为 MoE 层耗时随 EP 增大不降反升，而计算量并没有变。

            Ulysses 档：TP × CP ≤ 每节点卡数 软约束

            Ulysses 的 all-to-all 与 TP 的 all-reduce 争的是同一批头，也争同一条链路， 两者的组内卡数是乘起来的 —— TP 单独没超节点、乘上 CP 就超了，是这一档特有的坑。 而且这次 all-to-all 和 TP 的 all-reduce 一样在关键路径上，重叠不掉。

            与「TP 组不跨节点」同一档，黄色横幅提示、不拦截。 Ring 档没有这条：它的 KV 轮转是点对点、可与计算重叠，跨机代价小得多 —— 序列长到非切不可时，这正是换档的理由。

            PP 的 micro-batch 数 ≥ PP（交错式：≥ PP × VPP） 软约束

            流水线的 micro-batch 数太少，气泡（bubble）占比就上去了： 1F1B 下气泡比例约 (PP − 1) / micro_batch_num， 交错式（VPP > 1）把它按 1/VPP 缩小，代价是在飞激活变多。 要把气泡压到 10% 以下，micro-batch 数大致得是 PP 的十倍。

            但 micro-batch 数受全局 batch 约束，两头都紧时只能回头压 PP。 开了 VPP 之后门槛还要再抬一档：micro-batch 数少于 PP × VPP， 交错换来的那点气泡收益直接归零 —— YAML 视图的 micro_batch_num 已按此取值。

            单卡显存由什么构成

            第三关是唯一一个「配得通、也切得开，却仍然跑不起来」的关卡。 要估它，得先把一张卡上的显存拆成六段，再看每一段被哪一维切：

            段大小被谁切
            权重参数量 × 2（bf16；随精度档变：主权重 fp32 时 4、FP8 档 1）见下表
            梯度可训练参数量 × 2（主权重 fp32 时 4）
            优化器状态可训练参数量 × 12（fp32 master + momentum + variance）；主权重 fp32 时只剩 8（master 就是参数本身）
            激活 每层 ≈ 34 · mb · s · h（不重计算 + 开 SP）；选择性掉到 17、全开掉到 2 ÷ TP、÷ CP，× 在飞的 micro-batch 数（VPP 会把这个份数抬上去，micro_batch_num 会把它夹下来）
            运行时底座驱动 + context + kernel binary，几个 GB不随配置变
            预留 buffer / 碎片通信 buffer + 算子临时区 + 分配器碎片随并行配置变，见下

            参数相关的三段各自被谁切

            MoE 模型不能套 dense 的 12H²/层 经验公式： 一个 92B 的 MoE 模型可能有 97% 的参数在专家里，套 dense 公式会算出一个完全错的数。 必须逐项分算：

            这一项被谁切
            路由专家÷ EP，再 ÷ ETP（若有）　← MoE 下减容器的主力
            共享专家÷ TP。在 EP 域内每卡复制一份完整的，EP 帮不上忙
            Attention / Dense MLP÷ TP
            router / gate不切。量级小，但逐层累加不完全可忽略
            Embedding / LM Head看 vocab_emb_dp：走 DP 则不切、每卡背满，走 TP 才 ÷ TP。本页已落成一枚开关，默认走 DP
            以上全部÷ PP，体现为「这张卡只背本 stage 那几层」
            DP不切，除非拨了「权重分片」：ZeRO-1 档优化器状态 ÷ DP，FSDP2 档权重 / 梯度 / 优化器三段全 ÷ DP（另加 all-gather 暂存）。本页已落成一枚三档控件，默认 ZeRO-1
            每个数几个字节由精度两档定（计算精度 / 主权重精度）：主权重 bf16 时是 2 + 2 + 12，fp32 时是 4 + 4 + 8（合计都是 16 B，变的是哪一段扛着），FP8 档权重那一份再减半。本页已落成两枚档位控件，默认 BF16 / BF16
            可训练与否上面几行说的是「一张卡上有多少参数」。而梯度与优化器状态那 14 B 只按可训练的那部分算 —— 开 LoRA 后主干冻结，这两段只剩每层 4·r·2H 个 adapter 参数的份，权重段一个字节不少。本页已落成一枚开关加一枚 Rank，默认关

            三条不能省的细节

            • 各 stage 不等重。层数本来就可能不均（46/4 → 12,12,11,11）， 首段还多背 embedding、末段多背 LM head。 看平均值没有意义 —— OOM 只需要一张卡爆，要看的是最紧的那张。
            • 激活要乘在飞的 micro-batch 数。1F1B 下 stage s 同时压着 PP − s 份未反向的激活， stage0 最紧。忽略这一项会系统性低估最危险的那张卡，而且 PP 越大低估越多。 开了虚拟流水（VPP > 1）换成交错式调度，份数变成 [2(PP−s−1) + (VPP−1)·PP + 1] / VPP —— 整排小柱一起抬高、而且变平， 末段抬得比首段还多。这就是 VPP 的账：气泡按 1/VPP 缩小，代价全记在这里。 反过来，一共只有 micro_batch_num 那么多份可灌：少于 warmup 深度时 在飞份数按 min(公式, micro_batch_num) 夹下来，整排小柱一起矮下去 —— 那不是配置变省了，是流水线没灌满（气泡换来的）。
            • 运行时开销不是固定百分比。按已用量抽一个比例，等于把一个几乎不随模型变的量做成正比项： 大 EP / 大 PP 的轻卡被低估（光驱动加通信域就不止那点），重卡又虚高。

            预留那一段随什么变

            项跟着什么走
            通信 buffer∝ 通信域个数。每个 >1 的并行维一个，MoE 的 all-to-all 另起一条
            算子 workspace∝ 一层的 token 张量。峰值由单个最大算子决定，不是全部层的和
            分配器碎片∝ 已用量。六段里只有这一项本来就该按比例算

            为什么不能卡到 100%

            上面算的都是稳态值，而通信 buffer 与碎片本身还在逐 step 波动。 经验上越过 70% 之后这点波动就足以把余量吃光，越过 88% 基本是在等 OOM —— 那时候「还没满」并不等于「跑得下」。留出的那一截不是浪费，是波动的容身之处。

            显存不够时该动哪一维

            这是前面所有约束真正咬合的地方：每一项都能换来显存，但每一项的代价落在不同的地方， 而且都会反过来触发前两关的约束。

            动这个省下什么代价会撞上
            提 EP路由专家的权重/梯度/优化器状态，MoE 模型里最大的一块 all-to-all 通信域变大E % EP、可能还有 DP % EP
            提 PP每卡少背几层，三段参数一起降 流水线气泡变大；stage0 的在飞激活反而增加num_layers ≥ PP、micro-batch 数
            提 TP参数与激活一起降，见效最直接 通信最密的一维，跨节点即悬崖头数 / KV 头数 / intermediate 的整除，以及每节点卡数
            提 CP只降激活，长序列下才有意义 attention 内部多一轮通信（Ulysses 一次 all-to-all / Ring 逐块轮转） Ulysses 撞 num_heads % (TP×CP)，Ring 撞 seq % (2×CP)
            提 VPP什么都不省 —— 反而更费 在飞激活变多，整排小柱一起抬高 num_layers % (PP×VPP)；它买的是气泡不是显存，列在这里是为了别把它当省显存的旋钮
            重计算 → 选择性激活正好减半（每层 34 → 17：只重算 FFN 段） 反向多算两三个矩阵乘，比全开便宜得多不撞整除约束 —— 显存只差一点时先试这一档
            重计算 → 按层数停在任意中间高度：每个 stage 的前 N 层按全开算 只有被选中的那几层付重算的账 不撞整除约束；N 按各段层数截断，这是唯一逐 stage 分别生效的一档
            重计算 → 全开激活掉一个数量级（每层 34 → 2） 反向多跑一遍完整前向，约 +30% 算力不撞整除约束，是最容易先试的一项
            开 LoRA梯度段与优化器段几乎归零（那 14 B/参数只按 adapter 算） 换了一种训练：主干冻结，只在 adapter 里学 不撞整除约束，但激活一点不省；只有这一跑本来就是微调时才谈得上
            权重分片 → ZeRO-1优化器状态 ÷ DP，权重相关字节里最大的一块 每步多一轮 all-gather需要 DP > 1 才有效（DP=1 时本页把控件置灰）
            权重分片 → FSDP2权重 / 梯度 / 优化器三段全 ÷ DP（ZeRO-3 口径） 每层一轮 all-gather，外加约 2 层权重的暂存 同上；与 TP/PP/CP 同用属两条路线混用，本页给软警告
            降 micro-batch激活线性下降 算子效率下降，且要靠梯度累积把全局 batch 补回来micro-batch 数与流水线气泡
            加 DP什么都不省 —只增吞吐，是这张表里唯一的例外
            顺序上的经验：先试不撞任何整除约束的那两项（重计算、权重分片 → ZeRO-1）， 它们只在算力和一轮通信上付账 —— 而重计算有四档，别一步拨到底： 差得不多时「选择性」（减半）或「按层数」就够，把算力留给真正需要的地方。 还不够就把权重分片再往上拨到 FSDP2 （压得最多，但通信从每步一轮变成每层一轮）；再考虑 EP / PP，它们要重新对整除关系； TP 放到最后 —— 它同时被模型结构和节点边界两头夹住，是最容易一提就撞墙的一维。
            LoRA 不在这条顺序里：它不是「显存不够时的下一步」，而是换一种训练。 这一跑是微调就该一开始就开着，是预训练就一直关着。
